## 1. Context, compaction and prompt caching

### How it works today
- The app never knows which real model answers. It plans every request against a fixed **48k** working window for any `telesia-*` alias (`ContextWindow`).
- When a request estimate passes about **36k**, older history is silently folded into a short summary (made by `telesia-fast`, at most 300 words). The latest turns stay word for word. The user sees nothing.
- Safety net: if a model still answers "request too large", the app compacts and retries once by itself.
- The proxy picks routes only by order and health, not by context size.
- The allowance already charges cached input at 0.1 when the provider reports cached tokens.

### Gap
A fallback route with a smaller window than the request would fail or truncate. Every fallback or key rotation also restarts the provider's prompt cache from zero.

### Plan: invisible model swaps
1. Store each model's **context size** in `ai_models` (dashboard field, can be read from the provider's model list).
2. Before trying a route, the proxy estimates prompt tokens plus reply room and **skips routes that cannot fit**, moving to a larger one. No error reaches the phone.
3. Rule: the app's 48k budget always stays **below the smallest model** in `telesia-smart` and `telesia-vision`. The dashboard warns when a smaller model is added to those aliases.
4. Optional: the proxy returns `x-telesia-window` (the smallest window of the alias's healthy routes), so the app can stretch or shrink its budget on its own.

### Plan: prompt caching
Caching is per provider and model, and for Gemini per key and project too.
1. **Sticky chats.** The app sends a chat id header (`x-telesia-chat`). The proxy pins that chat to the same route and key for about 10 minutes while it stays healthy, and switches only on failure. Agent steps within one task then reuse the cache.
2. **Stable beginning, changing end.** Things that never change go first, in a fixed order: core instructions, then tools. Things that change go last: clock/date, memory, step notes, screenshots. (Check: the clock line likely sits inside the system prompt today and breaks the cache every minute. Move it to the end.)
3. **Fixed tool order.** No reshuffling between steps. Connector tools are appended at the end.
4. **Cache-friendly compaction.** Summarize in bigger, rarer chunks so the beginning stays the same for many steps.
5. **Measure.** Log cached tokens per request and show the cache-hit rate per route in the dashboard.

### What a swap keeps
History is in the standard OpenAI format, so tool calls and results move between models cleanly. The previous model's hidden reasoning is dropped. Model-specific junk (e.g. DeepSeek DSML) is already stripped by the proxy.

### Suggested order
1. Context sizes and the fit check in the proxy
2. Sticky chats
3. Reordering the prompt for caching
4. Cache stats in the dashboard

## 2. Bots

### Where they are today
Bots already have identity and persona, memory, a desk, routines, follow-ups, notification watches, a journal, lessons, a knowledge sandbox, scoped apps, powers (web/browser/phone/files/apps), an interruption budget and a per-bot token budget. There is also a Bot Store (publish and hire), four built-in templates (Nova, Amal, Rank, Ustad) and Offices (a Chief plus teammates, a task board, work hours, approvals).
**Weak spot:** everything runs on the phone. Routines, heartbeats and follow-ups are phone alarms, so Doze, OEM battery killers (Xiaomi, Samsung...) or a dead battery break the main promise.

### 2.1 Dependable: "works while you sleep"
- **A cloud brain for bots.** A Supabase cron plus a `bot-run` edge function runs everything that doesn't need the phone: web, research, email and connected apps, briefs, Office planning. The phone only handles phone powers (texts, screen, notification watches).
- **Push, not polling.** Results arrive by FCM notification, so the app doesn't need to be alive.
- **Cloud sync** of bot memory, desk and journal. They survive a reinstall and can later work across devices.
- **Health line on each bot:** "Last worked 8:02, next 18:00", with a clear fix when the phone blocks it (battery exemption).

### 2.1 design (2026-10-19, part A built: sync; part B built: `bot-run` + cron + push, see docs/cloud-proxy.md "Cloud runner")
Bots stay phone-first: the phone keeps a full copy and works offline. The owner's account holds a second copy so a bot survives a reinstall, comes back on a new phone, and can work in the cloud when the phone is off.

**What syncs** (migration `supabase/migrations/20261019_bot_cloud.sql`, app `lib/services/bot_sync.dart`)
- `cloud_bots`, one row per bot: `setup` = everything that says who it is and how it works (name, role, persona, mission, instructions, first meeting, icon, voice, routines, follow-ups, notification watches as settings, powers off, sandbox, apps by name only, scoped apps, lessons, skills ids, token budget, reach-out level, heartbeat, quiet hours, calls allowed, hired/paused, its chat id, store id, "Works in the cloud" choice); `knowledge` (notes and files' text, sent only when its hash changes); `schedule` = the jobs the cloud may run, already resolved by the phone (`{id, type: routine|followup|heartbeat, time, days, kind, do, next|at (UTC), every_hours}`); `cloud_enabled` (hired and "Works in the cloud" on); `next_run_at` (UTC, earliest job); `tz_name`, `tz_offset_min` (routine times are phone-local).
- `cloud_bot_memory`, one row per memory line (`item_id` = hash of the line). `cloud_bot_desk`, one row per task (`item_id` = task id). Removed items stay as tombstones (`deleted = true`).
- `cloud_bot_journal`, append-only, newest 500 per bot. A cloud run adds rows with `origin = 'cloud'`; `chat` carries its full message, which the phone posts in the bot's chat (one message id per entry on every phone).
- Up: a few seconds after any change, only what changed (hashes per bot, per line, per task). Down: on sign-in, all rows the first time on a phone (a new phone gets its bots back), then rows newer than the last pull (2 min overlap, merges are idempotent). Rows a phone wrote itself are skipped on later pulls (`device_id`).
- Server: `updated_at` and `version` set by trigger, row owner fixed, RLS own rows only, size checks on every column, caps (60 bots, 1,000 memory and desk rows per bot). Phones may write only phone-owned columns; `run_state`, `last_run_at`, `run_lock_until` are the cloud's (service role).

**What never syncs**: phone-only data (texts, contacts, phone calendar, notification contents, screen, files on the phone, call audio), logins, passwords, keys and tokens (app sign-ins stay on the phone; setup text, desk text and journal text pass `BotPackage.scrubSecrets`, and a memory line that looks like it holds a key stays on the phone), the day's counters (messages, calls, tokens used), run traces.

**Conflict rule**
- Different items always merge (memory lines, desk tasks, journal entries).
- The same item changed on this phone and elsewhere since the last round: this phone's version wins (it is sent right after). Setup is one item.
- Removing a bot wins everywhere (tombstone row; its lines are deleted).
- Journal only grows; never edited.
- Ownership: the phone owns setup and schedule; the cloud owns `run_state` (`{"done": {"<job id>": "<iso>"}}`), `last_run_at`, `run_lock_until`, and adds memory, desk and journal rows with `origin = 'cloud'`. The phone drops follow-ups listed in `run_state.done`.

**Which jobs are cloud-eligible**: a routine, follow-up or heartbeat that needs no phone power: not `kind = call`, and (unless the bot's phone power is off) its instruction does not mention texts, notifications, WhatsApp, the screen, contacts, the phone, calls, photos, the camera, the clipboard or the battery (`Bot.needsPhone`). Web, research, briefs, documents and connected apps are cloud work (apps once their sign-ins live server-side, Plan 4; until then a cloud run says which app it needs). Notification watches are always phone-only. "Works in the cloud" defaults on when none of the bot's routines needs the phone (`Bot.cloudFit`); the owner can switch it (`cloudChoice`).

**Hand-over**: setting `bot_cloud_runner` (`ai_settings`, read by the app via `bot_cloud_info()`) is false. While false, phones run everything as before. When part B sets it true, a phone stops setting alarms for jobs the cloud owns (bot hired, "Works in the cloud" on, job eligible); jobs that need the phone keep their alarms.

### 2.2 Cheap: bots don't eat the allowance (background lane + office caps built 2026-10-19, see project-state)
- **Check first, work second.** Each wake starts with a tiny `telesia-fast` check: did anything change, is it worth doing? Most heartbeats end there for a few hundred tokens.
- **No wake without a reason.** Prefer triggers (new email, a watched page changed, a notification) over "every N hours".
- **Background lane.** Bots and Offices get their own share of the daily allowance (about 30%), so they never block the user's own chats. When it runs out they pause politely.
- **Cache-friendly layout.** Persona, instructions, knowledge and tools stay the same in every run and go first. Each run's fresh input goes last.
- **Office caps.** A Chief plans once per work block. A teammate gets a set step budget per task.

### 2.3 Useful: a visible win in the first minute
- **Hire to first result in about 60 seconds.** Three quick questions, then the bot does one real task right away.
- **Results as cards** (a brief, a table, a doc, a draft ready to approve), not walls of text.
- **Weekly report card:** "Nova this week: 5 briefs, 2 drafts, saved you about 3 hours." It shows value and makes a nice screenshot.
- **Trust controls:** approvals before sending, paying or posting; undo where possible; a clear activity log; the interruption budget that backs off when ignored.

### 2.4 Shareable: the marketing engine
- **A public page for every bot** (`telesia.site/b/<name>`): what it does, an example result, a "Hire in Telesia" button with a deep link.
- **Bot Store polish:** categories, trending, creator profiles, hire counts, sample outputs.
- **Rewards for creators and referrers:** more daily allowance when people hire your bot or join through your link. **Built 2026-10-19 (v1.13.24+57)**: 30k/day for 7 days per new sign-up through your link/code or first hire of your published bot; caps 150k/day earned, 20 lifetime, 5 a day, 7-day new-account window; no self/own bot, one inviter per account, same-phone guard; all in `ai_settings` (dashboard Settings + Rewards tab, admin gifts and revokes). Details in project-state "Plan 2.4: rewards".
- **Results you can share** with a small "made by <bot> on Telesia" footer. **Built** (bot replies shared from a bot chat; links to the bot's page or the sharer's invite link).
- **Ready-made bot packs** for target groups: students, small shops, job seekers (ties in with the resume product), creators, Muslim users (prayer/Quran tools exist).

### 2.5 Safe store
- Check every published bot before it goes live: hidden instructions, data grabs, attempts to exfiltrate contacts.
- Shared copies never carry the owner's memory, knowledge files or connections, only the setup. Show a clear "what this bot can do" list before hiring.
- Report and remove, plus admin moderation in the dashboard. Dashboard part built 2026-10-19: Unpublish per bot in the user container, published setups readable, automatic safety flags.

### 2.6 Measure (built 2026-10-19: `events` table, `log_events`, ai-admin `events_summary`)
Events in Supabase: hired, first result, replied to vs ignored, kept after 7 days, shared, hired from a share.

## 3. Memory for voice calls

### Why calls feel forgetful (from the code)
- `LiveController.start` sends `persona + app.liveSystemPrompt()`. `liveSystemPrompt` is the **full chat system prompt** (card rules, deep research, shell, pages...) plus the clock and the Live rules. User memory (`memory.promptSection()`, up to 80 facts) sits deep inside it, and up to **120 tool declarations** are sent too. Voice models are weak at finding something buried that deep.
- **No conversation history** is sent. A call doesn't know what was discussed in chat minutes earlier.
- **Nothing is learned after the call.** The transcript is saved (`saveLiveTurns`), but no facts, tasks or summary are extracted.
- Bot calls put the bot's memory, desk and journal in the persona (`Bots.promptOf`), but the same huge app prompt follows and drowns it.
- Not a proxy issue: `/live-token` issues a single-use token without `liveConnectConstraints`, so the app's `systemInstruction` is honored.

### Plan, cheapest first
1. **A short call prompt (free, saves tokens).** A Live-only prompt of about 1.5k tokens: identity, a **"What you know" block at the top**, the voice rules, and the `live_task` handoff rules. Drop the chat-only parts. Live re-processes the context every turn, so this also makes calls cheaper.
2. **"What you know" block (free).** The top ~20 user facts. For a bot, also its own memory, open desk tasks and its last 5 journal lines. Capped at about 600 tokens.
3. **"Last time" recap (free).** The chat's existing compaction summary plus the last ~6 turns of that chat, trimmed to about 800 tokens. Calling a bot uses the bot's chat, calling Telesia uses the current chat.
4. **`recall` tool (free, local).** Searches facts, bot memory, the journal and past chat summaries on the phone, only when needed.
5. **After the call: one small save (about 1-2k tokens).** If the call had at least 2 real turns, one `telesia-fast` pass over the transcript returns:
   - a 3-line summary posted into the chat (so chat and the next call know)
   - new facts, sent to `remember` / `bot_remember`
   - promises, which become desk tasks or follow-ups for bots
6. **Long calls don't forget mid-call (free).** Enable Live `contextWindowCompression` (sliding window) and `sessionResumption` in the setup.
7. **Fewer tools on calls.** A small core set plus `live_task` for heavy work: faster connect, fewer wrong tool picks.

### Cost
Steps 1-4 and 6-7 add no model calls and shrink the per-turn context, so calls end up cheaper than now. Step 5 is the only paid step.

### Test
On the dev APK, ask the same question ("what's my name and what are we working on?") before and after, for both a Telesia call and a bot call.

## 4. Apps rebuild (connectors for non-technical users)

Decision (2026-10-18): **free forever, no middleman.** No Composio or similar broker at launch. Launch uses only methods that need **no developer registration**; registered OAuth apps (Microsoft first) come later.

### Where it is today
- `lib/services/connector_catalog.dart` (~53 connectors), `lib/screens/connectors_screen.dart`, `lib/services/connector_tools.dart`.
- Almost every connector is "paste a key or token". No general OAuth. Hard for non-technical users.

### New layout: three rows
1. **Apps**: real logo, plain-language "what it can do", one **Connect** button. Covers phone apps, one-tap hosted MCP apps and (later) our own OAuth apps. The user never sees the words MCP, OAuth or token.
2. **MCP**: advanced. The user pastes a remote MCP server URL; OAuth where the server supports it.
3. **API**: power users. Manual keys/tokens (existing key connectors move here, e.g. Telegram bot token).

### Launch tier A: on the phone (no sign-in, no registration)
- Calendar via Android CalendarContract (reads every account on the device, Google included). Read + add events.
- Contacts via Android Contacts.
- Gmail drafts via the Gmail compose/share intent (user taps Send in Gmail).
- Reminders, alarms, SMS draft (already exist).

### Launch tier B: hosted MCP with one-tap sign-in (no registration)
Note: `lib/services/mcp_oauth.dart` already does this on the phone (discovery, dynamic client registration, PKCE, loopback 127.0.0.1 callback) with presets for Notion, Canva, Airtable, ClickUp, monday, Asana, Atlassian, Linear, Miro, Granola, Krisp, Jotform, Intercom, Close, Zapier. Plan = reuse it, test each preset, and move tokens server-side so cloud bots can use them.
How it works:
1. User taps **Connect** on e.g. Notion.
2. Our server calls the vendor's hosted MCP endpoint; it answers 401 with its OAuth metadata.
3. Our server registers Telesia on the spot (OAuth Dynamic Client Registration / Client ID Metadata Document: name "Telesia", logo, redirect URL) and gets a client id. No portal, no secret, no review.
4. Chrome Custom Tab (never WebView) opens the vendor's consent screen ("Telesia wants access"); PKCE + state check; back to `telesia://apps/connected`.
5. Tokens encrypted server-side in Postgres; phone only gets connection status. Refresh cron before expiry.
6. The vendor runs and maintains the tools; we call them.

Candidates (each must be **tested** before launch; keep only those that really allow dynamic registration): Notion, Linear, Atlassian (Jira, Confluence), Asana, HubSpot, Stripe, Canva, PayPal, Square, Sentry, Cloudflare, Intercom, possibly Todoist and Monday. Target: ~20 apps across tiers A + B.

Not covered at launch: Gmail reading, Outlook, Slack, GitHub, Dropbox, Google Drive, YouTube, Spotify, Zoom, Strava, Instagram, X. (WhatsApp: built on dev 2026-10-19 as a phone plugin, "Path 2": notification access + phone control, no WhatsApp Web / unofficial client / Meta API; see project-state "WhatsApp on the phone".)

### Later tier C: our own registered OAuth apps (free registrations)
- Generic `oauth` edge function: each app is a **config row** (auth URL, token URL, scopes, client id; client secret in Supabase Vault) + one small adapter (3-6 actions).
- Order: **Microsoft** first (one app = Outlook mail + calendar, To Do, OneDrive, Teams), then GitHub, Slack, Dropbox, Discord, Trello, ClickUp, Airtable, Box, Calendly, Figma, GitLab.
- Google: `drive.file` needs no audit; Calendar/Gmail send need free verification (weeks); Gmail reading needs the paid yearly security assessment, so it comes last. Until then: phone calendar + Gmail drafts + Outlook for inbox reading.
- Re-verify every provider's current terms, review rules and user caps before registering.

### Server pieces
- Edge function `apps`: `catalog`, `mine`, `connect`, `callback`, `disconnect`, `run`.
- Tables: `app_catalog` (slug, name, logo, category, featured, order, source = phone | mcp | oauth | api, visible), `app_connections` (user, app, account label, encrypted tokens, scopes, status, last used, last error), `app_tools` (per app: curated tool, friendly name, description, access level, enabled).
- Dashboard page: pick/rename/enable tools per app, hide/show/feature apps, see connection health and errors. No app update needed for catalog changes.
- Daily check of each MCP server's tool list; alert in the dashboard when tools change or a server fails.
- Delete account also revokes and deletes all app connections.

### How the agent uses Apps (cheap)
- The model sees only **two tools**: `apps_find("send email")` returns the 3-5 best actions among the user's connected apps; `apps_do(action, args)` runs one. Never the raw tool catalogs.
- Results trimmed server-side before reaching the model.
- Not connected yet: `apps_do` returns an in-chat **Connect card**; after the callback the interrupted task resumes automatically.
- Bots use the same two tools, limited to the apps the owner allowed for that bot (`appsScoped`).

### Permissions and safety
- Per app and per bot: **read only / drafts only / act with approval**.
- Sending, posting, deleting, paying always show a preview card and need approval.
- App card shows: what it can do, read/write access, connected account, last used, health, Reconnect / Disconnect.
- Health check marks a broken connection "Reconnect" before the user hits an error; a vendor outage shows "resting", never a raw error.

### Logos
Official brand assets or Simple Icons, cached in Supabase Storage, with a letter-tile fallback. **Built 2026-10-20 (v1.13.33+66) as bundled assets** (`assets/logos`, `BrandLogo`): Simple Icons marks in brand colour + site icons for the rest; moving them to Storage can wait for the server catalog.

### Suggested order

2. Generic MCP client + dynamic-registration OAuth in `apps`; test the candidate list and keep the ones that work.
3. `app_tools` curation + dashboard page.
4. App cards, Connect card in chat with auto-resume, permission levels.
5. Move key connectors to the API row; MCP row for custom servers.
6. Later: register Microsoft, then the tier C list; Google verification in parallel.

## 5. Telesia as a real coworker (UX cleanup and digital employees)

Goal: smooth, luxury, modern, simple and powerful. Today it has an employee's abilities but a dev tool's controls.

### The idea
Telesia is **a team that works for you**. Every screen answers one of:
- **Talk**: ask anything (chat, call, Telegram).
- **Team**: who works for me and what they are on.
- **Today**: what got done, and what needs me.

### 5.1 Navigation: 9 items to 4
Now: New chat, Bots, Offices, Skills, Apps, Library, Files, Scheduled, Archived, plus Projects.
New: **Today · Team · Apps · Files**, then Projects and chats.
- Today (new home): "Needs your OK" cards, done while you were away, routines (replaces Scheduled).
- Team = Bots + Offices merged; an office is "a team with a lead".
- Files = Library + Files + Trash.
- Skills leave the menu; bots install them silently (list stays under Advanced).
- Archived becomes a filter in chat search.

### 5.2 Bots that feel like employees (built 2026-10-19: v1.13.27+60 employees, v1.13.28+61 Offices into Team; details and the decisions made while the owner was away in project-state)
- **Hire, don't build**: pick a role, answer 3 short questions, a real first result within a minute.
- **Job page**: Responsibilities ("Every morning: brief my inbox"), Working on, Done, Needs you. Replaces separate desk/routines/watches views.
- **Reports like a person**: short daily/weekly note in its chat; step traces hide behind "How did you do it?".
- **One approval card** everywhere: Approve · Edit · Not now; similar asks batched ("3 emails to send").
- **Trust levels instead of toggles**: New (asks before every action) -> Trusted (does routine work; still asks for money, sending, deleting). Offered after ~10 approvals with no edits. Replaces "Ask before risky steps" and permission switches.
- **Training tab**: Instructions + Knowledge sandbox + Lessons become one page: Tell it · Give it files · What it learned from your corrections.
- **Presence**: avatar, voice, status (Working · Free · Off); "can call me" and full-screen calls in one Calls setting.
- **Offices**: keep team, lead and shared task list; drop separate board and Docs tabs (Docs = the team's folder in Files). `offices_screen.dart` is ~1,650 lines; aim to cut about half.

### 5.3 Remove or hide
- Steps per task, Size limit per task (server decides).
- Easy mode (make the normal app simple; one app to maintain).
- Show working steps toggle (replaced by a tappable "Worked 40 s" chip).
- "Auto compacted" label in chat.
- Workspace folder, Trash (move into Files).
- "Add an MCP server" / "Add your key" inside a bot (bots pick from connected Apps).
- Zapier off the featured list (free tier is capped).

### 5.4 Things in the wrong place

- Saved logins (Settings) -> Apps: "Websites I can sign in to".
- Memory (Settings) -> profile: "What Telesia knows about you", plain sentences, edit/delete.
- Let it take action + Phone permissions + Phone files -> one **Phone access** page with a check per item.
- Hello Telesia + voice for calls -> one **Voice** page.
- Settings becomes: Account · About you · Reply style · Phone access · Voice · Notifications · Privacy · Help.

### 5.5 Luxury feel (first pass built 2026-10-20, v1.13.33+66: serif titles, soft lines, approvals slide away, done tick, skeletons, empty hints, friendly failures; details in project-state)
- One type system: serif for titles, clean sans for text, generous spacing, almost no borders/dividers.
- Soft motion and haptics: approvals slide away, small check when a task is done.
- Skeleton loading instead of spinners; empty screens show one tappable example.
- Friendly failures: never "Couldn't..."; e.g. "Gmail is resting, I'll retry in 5 min".

### 5.6 Make sure it works

- 15 golden-path checks on a real phone: hire a bot, first result, approval, call, overnight routine, connect an app, etc.
